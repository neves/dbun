# dbun design decisions

A running log of every design decision so far. The hard-to-reverse ones also have an ADR in [`docs/adr/`](adr/). Terms follow [`GLOSSARY.md`](../GLOSSARY.md).

**Status key**

- **Confirmed**: stated or explicitly chosen by the owner.
- **Proposed**: recommended during design, not yet answered with a yes or no.

## 1. Scope

| Decision | Status |
|---|---|
| Embedded library for Bun on `bun:sqlite`. No server, no network protocol, no sync. | Confirmed |
| The client never writes or runs a migration. | Confirmed |
| The API is synchronous (no promises). Transactions are `db.transaction(() => …)`. | Confirmed |
| Documents are plain JSON in named collections; a collection exists from its first insert. | Confirmed |
| No runtime validation in the lib. Clients can plug in Zod or similar at their own boundary. | Confirmed |
| Document types come from caller-supplied TypeScript generics. | Confirmed |
| References are plain id strings and are never enforced (no dangling-reference checks, no cascades). | Confirmed |
| The lib is multi-tenant by default. | Confirmed |
| The lib can describe itself well enough for an admin interface to be generated later (standard label, timestamps and references). The interface itself is a separate later package. | Confirmed (goal); package split Proposed |

## 2. Tenancy

| Decision | Status |
|---|---|
| One SQLite file per tenant, inside one data directory. See ADR-0001. | Proposed |
| Collections are reachable only through a tenant handle: `db.tenant("acme").posts`. A single-tenant app calls `db.tenant("default")` once. | Proposed |
| Data shared across tenants lives in one reserved shared file (`db.shared`), with tenant documents holding plain ids into it. | Proposed |
| The lib keeps a bounded cache of open file handles and reopens on demand. | Proposed |

## 3. Physical schema

Identical in every tenant file. See ADR-0002 and the SQL below.

| Decision | Status |
|---|---|
| One `documents` table for all collections, with a `collection` column. | Proposed |
| Lib-owned columns: `id`, `collection`, `key`, `data`, `version`, `created_at`, `updated_at`. Everything else (status, flags, authorship, ordering) is an ordinary JSON field. | Proposed |
| The lib records a format version in `PRAGMA user_version` and upgrades files in place when needed. | Proposed |

```sql
CREATE TABLE documents (
  id         INTEGER PRIMARY KEY,      -- 64-bit, time-sortable, generated by the lib
  collection TEXT    NOT NULL,
  key        TEXT,                     -- optional external id, unique per collection
  data       TEXT    NOT NULL,         -- user JSON, without lib-managed fields
  version    INTEGER NOT NULL DEFAULT 1,
  created_at INTEGER NOT NULL,         -- epoch milliseconds
  updated_at INTEGER NOT NULL
);
CREATE UNIQUE INDEX documents_collection_key ON documents (collection, key);
CREATE INDEX documents_collection ON documents (collection);  -- lists a collection in id order for keyset pagination

CREATE TABLE trash (
  id INTEGER PRIMARY KEY, collection TEXT NOT NULL, key TEXT, data TEXT NOT NULL,
  version INTEGER NOT NULL, created_at INTEGER NOT NULL, updated_at INTEGER NOT NULL,
  deleted_at INTEGER NOT NULL
);

CREATE VIRTUAL TABLE terms USING fts5(
  t, content='', contentless_delete=1, detail=none,
  tokenize="unicode61 tokenchars '=_'"
);
-- rowid = documents.id; t holds field=value terms, _ref=<id> terms, and plain words
```

## 4. Identity

| Decision | Status |
|---|---|
| The id is a 64-bit integer in storage, because 26 characters was judged too big. | Confirmed |
| At API level the id is always a string. | Confirmed |
| The API string is `<collection>_<base36 integer>`, so references stay self-describing. See ADR-0003. | Proposed |
| On collection-scoped calls the bare base36 part is accepted as input. The lib always returns the full prefixed id. | Proposed |
| A prefix that does not match the collection is "not found", never another collection's document. | Proposed |
| The `collection` column exists so the id does not have to carry the collection in storage. | Confirmed |

## 5. Lib-managed fields

| Decision | Status |
|---|---|
| `version` is an integer starting at 1, bumped by the lib in the same `UPDATE` that writes (no trigger). | Proposed (the need is Confirmed) |
| Writes accept an optional `{ version }` and throw `ConflictError` on mismatch. Without it the write is last-write-wins. | Proposed |
| `created_at` and `updated_at` are lib-managed, stored as epoch milliseconds, and returned to the client as `createdAt` and `updatedAt`. | Proposed (the fields are Confirmed; the unit is open) |
| `created_at` needs no index because the id is time-sortable. An index on `updated_at` is deferred along with sorting by it (see section 11). | Proposed |
| `tenant_file` is dropped. | Confirmed |
| `etag` is dropped. If one is needed over HTTP, the lib derives it from `id` and `version`. | Confirmed |
| `ttl_seconds`, `owner_id` and other app-flavored columns are dropped. Authorship and ownership are JSON conventions that hold ids. | Proposed |

## 6. Deletion

| Decision | Status |
|---|---|
| Soft delete must not make every query filter on a marker, and must not lose the deletion time. | Confirmed |
| Delete moves the row to `trash` with `deleted_at`, in one transaction, and removes its terms. Restore moves it back, bumps `version` and re-indexes. See ADR-0005. | Proposed |
| A purge deletes trash rows older than a cutoff. | Proposed |
| Deleting a document frees its `key`. A restore fails with `ConflictError` if the key was reused. | Proposed |
| A full change history (`changes` log) is out of the MVP. | Proposed |

## 7. Unique key

| Decision | Status |
|---|---|
| Each document has an optional `key`, unique within its collection, usable to fetch it. See ADR-0006. | Confirmed (idea) |
| API: `insert(doc, { key })`, `getByKey(key)`, `upsert(key, doc)`. | Proposed |
| The key is a lookup handle only. References use the `id`, never the key. | Proposed |
| The key is a string, unnormalized by the lib, and may change through `update`. | Proposed |

## 8. Indexing and search

See ADR-0004.

| Decision | Status |
|---|---|
| Every scalar field of every document is indexed automatically as a `field=value` term in one FTS5 table. | Proposed |
| An index is a performance hint only: every filter works on every field. | Proposed |
| Range and sort-by-field narrow with the terms first, then compare and sort in memory. A declared ordered index is a later opt-in. **Deferred, see section 11.** | Proposed, deferred |
| Reverse reference lookups are equality filters: `find({ authorId: id })`. `db.referencing(id)` returns every document holding that id in any field, through a field-less `_ref=<id>` term. | Proposed |
| Full-text word search lives in the same FTS5 table as the terms. | Proposed |

## 9. Writes and reads

| Decision | Status |
|---|---|
| Writes: `insert`, `set` (replace), `patch` (shallow merge), `delete`, plus `upsert` and `restore`. | Proposed |
| `get(id)` and `getMany(ids)`, where `getMany` returns documents in the order given and `null` for missing ones. | Proposed |
| `find(filter, { limit, after, order })` returns a page `{ items, next }`, where `next` is the id of the last item (or `null`); see section 11. `referencing` returns a flat array and can be narrowed to one collection. | Proposed |
| There is no relation API (`hasMany`, `belongsTo`). | Proposed |
| Many-to-many is an array of ids on one side, or a join collection with a composite `key` for unique pairs. | Proposed |
| Collection names are permanent (renaming would rewrite ids). | Proposed |
| `ownerId` and `tenantId` are naming conventions only; the lib does nothing special with them. | Proposed |
| A document's display label is the first non-empty string among `title`, `name`, `label`, else the id, with a per-collection override in the TypeScript schema. | Proposed |

## 10. Superseded earlier decisions

These were proposed in earlier rounds and are replaced by the entries above.

- Ids of the form `users:0192…`, then `users_<26 base32 chars>`: replaced by an integer id with a prefixed base36 API string.
- `id`, `createdAt` and `updatedAt` stored inside the JSON as ISO strings: now columns, merged back into returned objects.
- `tenantId` as a naming convention for tenancy: replaced by one file per tenant.
- One process opening one file: replaced by one process opening one directory of files.
- A collection's rows found by id prefix range: replaced by the `collection` column.

## 11. Decisions from the open-questions round

All Confirmed by the owner.

| Decision | Notes |
|---|---|
| **Full-text search**: every string field of every document is searchable automatically, through `posts.search("hello")`, scoped to one collection. | Ranking, prefix and phrase support, and tokenizer settings are still open (see section 12). |
| **Query language**: equality filters only, plus sort and limit, in the MVP. | This is narrower than the earlier proposal. Ranges (`gt`, `lt`), `in`, `not`, `or`, `exists`, nested paths, `count` and cursor pagination are deferred. The in-memory range design in ADR-0004 is therefore not part of the MVP. |
| **Collection access**: a typed schema object passed to `open`, so `acme.posts` is checked by TypeScript, with `acme.collection<Post>("posts")` as the dynamic fallback. | The contents of that schema object are still open. |
| **Client-supplied ids**: allowed on insert, but only a valid prefixed id for that collection that does not already exist. | Covers imports and restores. |
| **Concurrency**: one process per data directory in the MVP, using WAL mode. The id generator needs no worker bits. | The lib does not need cross-process locking. Whether it refuses to open a directory already in use is open. |
| **Tenant lifecycle**: a tenant is created lazily on the first `db.tenant(id)` use. Tenant ids are limited to lowercase letters, digits, `-` and `_` so they are safe filenames. The lib offers `db.tenants.list()`, `export` and `delete`. | The open-file cache size is still open. |

| **Pagination**: keyset pagination with the last id as the next token, not offsets. | `find(filter, { limit, after })` returns `{ items, next }`, where `next` is the id of the last item, or `null` at the end. Stable under inserts and deletes. |
| **Value matching**: `find({ age: 30 })` matches both `30` and `"30"`. | Numbers and strings compare loosely for equality. Stored and query values convert to a canonical string term. |

### Proposed from the same round

| Decision | Status |
|---|---|
| Results are ordered by id (creation order), ascending or descending, because that is the order the cursor and the index give cheaply. Sorting by other fields is deferred, since it would need a token carrying the sort value as well as the id. | Proposed |
| Replace the planned `(collection, updated_at)` index with `documents_collection ON documents (collection)`. SQLite appends the rowid, so listing a collection by id with `id > :after` is an index range scan. | Proposed |
| `find` with filters runs as one query joining `terms` to `documents`: `terms MATCH … AND rowid < :after ORDER BY rowid DESC LIMIT :n`, then filters on `documents.collection`. FTS5 supports rowid range and order natively (tested on Bun 1.4.3). | Proposed |
| Equality compares the canonical string of a value: numbers as `String(n)`, booleans as `true` and `false`, strings as they are. A filter value is converted the same way, so `30` and `"30"` produce the same term. | Proposed |
| A term is `<path>=<value>`, where the value is the canonical string **encoded** as lowercase base32 of its UTF-8 bytes. See ADR-0004. | Proposed |
| Nested objects index their scalars by dotted path (`address.city`). Each array element gets its own term. Objects and arrays themselves are not indexed. | Proposed |
| Full-text words are added to the same index as plain tokens, and are separate from encoded equality terms. | Proposed |

## 12. Still open

Each affects the public interface or the stored data.

1. **Full-text search details**: ranking, prefix and phrase queries, tokenizer and language handling, result limits, and how a search combines with an equality filter in one call. Ranked results cannot page on id, so search needs its own token.
2. **Null and missing fields**: is `null` indexed as a term, and how does a client ask for "field is absent"? Is there a size cap on indexed values (long strings stay searchable as words, but may not get an equality term)?
3. **What the typed schema object declares**: collection document types and the label override are clear. Is anything else (an ordered index later, a default sort) declared there?
4. **Limits**: collection name rules (underscores interact with id parsing), maximum document size, maximum key length.
5. **Durability and operations**: backup, vacuum after large purges, who schedules the trash purge, and whether the lib refuses to open a directory another process holds.
6. **Introspection for the admin interface**: how does "fields seen in this collection" work without a schema table or a scan?
7. **Rebuilding derived data**: a command to rebuild the term index from `documents`, and what happens when the term format changes between lib versions.
8. **Change notification**: are live queries or change events in scope at all?
9. **Per-document schema version**: is a `schemaVersion` JSON convention, with lazy upgrade on read, worth documenting as the answer to evolving shapes?
10. **Open-file cache**: the default size and eviction rule for tenant file handles.
11. **Unmeasured claims**: how many open SQLite files are practical, how long an index build takes, and how the integer-id and trash layout perform. None of these were benchmarked.
