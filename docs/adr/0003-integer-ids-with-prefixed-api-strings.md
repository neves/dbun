# Integer ids in storage, prefixed strings in the API

Status: proposed (the integer id is confirmed; the prefixed string form is not yet answered)

A document id is a 64-bit, time-sortable integer in the `id` column, generated by the lib. At API level it is always a string of the form `<collection>-<base36 integer>`, such as `users-1x9f2k4m7pq` or `user_profiles-1x9f2k4m7pq`.

Twenty-six characters (a UUIDv7 in base32) was judged too large, and an integer is the smallest and fastest SQLite key. But a bare number stored in a post's JSON looks like any other string, so the lib could not recognise a reference or build an admin link without declarations. The collection prefix keeps references self-describing, and the `collection` column keeps the prefix out of storage.

Hyphen `-` is used as the separator between the collection name and the base36 integer, while collection names use `[a-z0-9_]+` (snake_case). Both pass through URLs, filenames and logs unescaped, and splitting on the last hyphen unambiguously separates the collection from the base36 id.

**Consequences**

- Collection names must match `^[a-z0-9_]+$` (no hyphens in collection names).
- Collection-scoped calls also accept the bare base36 part, so URLs like `/users/1x9f2k4m7pq` work. The lib always returns the full prefixed id (`users-1x9f2k4m7pq`).
- A prefix that does not match the row's collection means not found, never a document from another collection.
- Collection names are permanent: renaming one would rewrite every stored reference.
- Ids are generated by the lib. Whether an import may supply its own is an open question.
